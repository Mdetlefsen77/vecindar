# HU-07 · Un cambio de rol rige en la próxima petición

> Como **administrador** quiero **que un cambio de rol se aplique enseguida** para **que alguien a quien le saco permisos no los siga usando con su sesión abierta**.

Estado: en curso · Rama: feat/HU-07
Seguridad: sí · cuenta con rol de gestión degradada que conserva un JWT vigente → panel `/admin`, APIs de gestión y datos de vecinos

## Decisiones
- (navigator) El rol actual se lee de la base en el callback `jwt` de `src/lib/auth.ts`, cuando no es un login, y pisa `token.role`. Así `session.user.role` llega actualizado a los 40 archivos que lo leen (páginas, APIs, `guard.ts` y el layout que arma el menú), sin tocarlos. Comprobado en `@auth/core` 0.41.0 (`lib/actions/session.js`): cada `auth()` decodifica el JWT y ejecuta `callbacks.jwt` y después `callbacks.session`. Cuesta una consulta por cada `auth()`.
- (navigator) Si la base falla al leer el rol, el callback sigue con el rol que ya tenía el token y lo registra con `console.error`. Si el callback lanzara el error, `@auth/core` borraría la cookie y un corte de la base dejaría deslogueado a todo el barrio.
- (refinamiento) En el login (`jwt` recibe `user`), el rol sale de `authorize`, como hoy: ya viene de la base y no hace falta otra consulta.
- (refinamiento) El proxy (`src/proxy.ts`) solo mira si hay token, no el rol: no cambia.
- (refinamiento) Las push por rol (`enviarPushAdmins`, `enviarPushVecinos`, `enviarPushSoloAdmin`) ya filtran por `usuario.rol` en la base (U-44): no cambian.

## Criterios de Aceptación
**CA-1 · Al sacarle el rol, lo pierde**
- **Dado** una cuenta con sesión vigente cuyo token dice `ADMIN` y en la base tiene `rol: VECINO`
- **Cuando** hace su próxima petición
- **Entonces** su sesión dice `VECINO`: `/admin` la redirige y las APIs de gestión le responden 403

**CA-2 · Al darle un rol, lo tiene**
- **Dado** una cuenta con sesión vigente cuyo token dice `VECINO` y en la base tiene un rol de gestión
- **Cuando** hace su próxima petición
- **Entonces** su sesión tiene ese rol, sin volver a loguearse

**CA-3 · El menú usa el rol actual**
- **Dado** una cuenta a la que se le cambió el rol
- **Cuando** carga una página del dashboard
- **Entonces** el menú se arma con el rol actual

**CA-4 · Si la base falla, no se cae la sesión**
- **Dado** una cuenta con sesión vigente
- **Cuando** la lectura del rol en la base falla
- **Entonces** la sesión sigue con el rol del token, sin error ni cierre de sesión, y el fallo queda en `console.error`

**CA-5 · El login sigue igual**
- **Dado** un login correcto
- **Cuando** se arma el token
- **Entonces** lleva el id, el rol y el lote que devolvió `authorize`
