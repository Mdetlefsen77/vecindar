## Decisiones
- (navigator) El workflow se prueba con vitest: se agrega `yaml` como devDependency y los tests leen `.github/workflows/recordatorio-parte.yml`. El script del paso se ejecuta con `bash` desde el test, con el entorno armado a mano y un servidor HTTP local en lugar del sitio. `js-yaml` ya está en `node_modules`, pero solo como dependencia de eslint: no se importa.
- (navigator) Comprobación manual: en `/done`, el script del paso contra `PORT=3001 npm run dev`. La prueba en GitHub (cargar el secret y la variable, y lanzar `workflow_dispatch`) recién se puede hacer después del merge, porque GitHub solo ofrece `workflow_dispatch` para workflows que están en la rama por defecto: queda en `pendientes.md` (R-1).
- (navigator) El workflow se escribe en `/pair`, guiado por los tests. La rama `feat/oficios-seguridad` (`57a4d34`, solo ese archivo) sirve de referencia y se borra en `/done`.
- (refinamiento) GitHub Actions y no Vercel Cron: el plan Hobby de Vercel solo admite crons diarios (ya decidido en el endpoint, `route.ts:8-12`).
- (refinamiento) Los crons van en UTC (Argentina = UTC-3, sin horario de verano): `30 11`, `30 16`, `30 21` y `30 2`. Comprobado con `tsx` contra `turnoRecienTerminado` de `src/lib/partes.ts`: `11:30Z` → MANANA, `16:30Z` → MEDIODIA, `21:30Z` → MEDIATARDE, `02:30Z` → NOCHE del día anterior en Argentina; `14:00Z` → `null` (la ventana es de 3 hs, abierta a la derecha).
- (refinamiento) Si el endpoint responde un error (401, 500), la corrida falla (`curl -f`), para que se vea en rojo en la pestaña Actions y GitHub avise por mail.
- (refinamiento) El endpoint no cambia: ya tolera la demora de GitHub (3 hs) y el mismo `tag` por turno evita avisos duplicados si corre dos veces.

## Criterios de Aceptación
**CA-1 · Corre media hora después de cada turno**
- **Dado** el workflow en `main`
- **Cuando** son las 08:30, 13:30, 18:30 o 23:30 de Argentina
- **Entonces** llama a `GET <SITE_URL>/api/cron/recordatorio-parte` con `Authorization: Bearer <CRON_SECRET>`, y cada una de esas horas cae en la ventana de `turnoRecienTerminado` de un turno distinto (los 4 cubiertos)

**CA-2 · Se puede correr a mano**
- **Dado** el workflow en `main`
- **Cuando** alguien con permisos lo lanza desde la pestaña Actions
- **Entonces** corre igual que el programado (`workflow_dispatch`)

**CA-3 · Sin configuración, falla con un mensaje claro**
- **Dado** un repo sin el secret `CRON_SECRET` o sin la variable `SITE_URL`
- **Cuando** corre el workflow
- **Entonces** termina con exit 1 y el mensaje `::error::Faltan el secret CRON_SECRET o la variable SITE_URL del repo.`, sin llamar al endpoint

**CA-4 · Si el endpoint falla, la corrida falla**
- **Dado** un endpoint que responde un error (por ejemplo 401 por un secret mal cargado)
- **Cuando** corre el workflow
- **Entonces** la corrida termina con un código distinto de 0
